# 1단계: 기사 제작과 검증 기준

이 문서는 처음 정리한 설계 기준입니다. 현재 구현·저장 구조와 최종 사용 순서는 README와 docs/final-guide.md를 참고하세요.

## 목적과 첫 화면

이 웹앱의 첫 화면은 운영자가 원문 기사를 넣고 검증을 준비하는 편집 화면입니다.
독자가 완성된 기사를 읽는 공개 웹사이트와 구분합니다.

PC에서는 왼쪽에 원문 입력, 오른쪽에 주장별 판정과 근거를 배치합니다.
현재 버전의 오른쪽에는 검증 전 표시와 근거 등록 기능이 있습니다.
휴대전화에서는 원문, 검증 영역 순서로 세로 배치합니다.

## 제작 흐름

원문 등록 → 사실 주장 추출 → 근거 확보 → 원문 검증 → 기사 재작성 → 편집 → 재작성본 재검증 → 사람의 승인 → 게시.

원문에 오류가 있으면 근거에 따라 바로잡거나 해당 내용을 제외하여 재작성할 수 있습니다.
원문의 모든 문장이 일치 판정을 받아야 재작성할 수 있는 것은 아닙니다.
발행 여부는 최종 재작성본의 검증과 현재 버전에 대한 사람의 승인으로 결정합니다.

## 주장별 판정

한 기사에 총점만 붙이지 않고 확인 가능한 사실을 나누어 판정합니다.
날짜, 숫자, 기관, 대상, 지역, 적용 연도, 범위, 예외와 조건을 함께 비교합니다.
아래 네 판정과 별도로 '검증 전 / 검증 중 / 검증 완료' 진행 상태를 둡니다.

| 판정 | 판정 기준 | 편집 시 조치 |
| --- | --- | --- |
| 일치 | 확인한 근거가 해당 주장의 핵심 사실과 적용 조건을 뒷받침한다 | 근거를 연결하고 표현을 유지하거나 쉽게 바꾼다 |
| 불일치 | 같은 대상·시점·조건의 신뢰할 수 있는 근거와 직접 모순된다 | 근거에 맞게 수정하거나 제외하고 다시 검증한다 |
| 조건 보완 필요 | 핵심 사실은 맞지만 대상·시점·범위·예외가 빠져 의미를 오해할 수 있다 | 빠진 조건을 넣고 다시 검증한다 |
| 확인 불가 | 근거 부족, 원문 접근 실패, 자료 간 충돌 등으로 결론을 정할 수 없다 | 필요한 근거를 확보하거나 최종 기사에서 해당 사실 주장을 제외한다 |

자료가 없다는 이유만으로 불일치라고 판정하지 않습니다.
일치 판정은 해당 주장에 대해 확보한 근거의 범위에 한정됩니다.
한 주장의 숫자 일부만 일치할 때 전체 문장을 일치 처리하지 않습니다.
날짜가 지난 자료나 다른 적용 연도의 자료를 현재 근거로 사용하지 않습니다.
근거 간 충돌이 해소되지 않으면 확인 불가로 두고 이유를 표시합니다.

예시:

- 동일한 공식 안내의 마감일과 원문의 마감일이 다름 → 불일치.
- 일부 대상자에게 적용되는 제도를 전체 대상 제도로 표현함 → 조건 보완 필요.
- 접속 실패로 마감일을 확인할 자료를 확보하지 못함 → 확인 불가.
- 대상·마감일·예외까지 같은 자료로 확인함 → 일치.

## 근거를 남기는 방법

가능하면 정책 발표 기관, 교육청, 학교, 대학의 공지·모집요강 같은 원자료부터 확인합니다.
언론 기사나 설명 자료는 보조 근거로 사용하고 출처의 성격을 함께 표시합니다.
기관명이나 도메인만으로 공식성과 정확성을 확정하지 않고 문서 제목, 발표일, 적용 연도와 대조 내용을 확인합니다.

각 판정에는 다음을 남깁니다.

- 검증한 원문 또는 재작성본의 주장과 위치.
- 자료 이름, 출처 주소, 발표일 또는 적용 기간.
- 해당 페이지·문단·표 위치와 판정을 뒷받침하는 짧은 발췌.
- 일치 여부를 설명하는 이유 및 수정할 사실·조건.
- 검증 시간과 기사·근거 버전 번호.

등록 시간과 검증 시간은 별도입니다.
기사의 출처 목록에 링크를 넣는 것만으로 검증을 완료하지 않습니다.
서버나 AI가 실제로 읽지 않은 자료를 '확인한 근거'로 표시하지 않습니다.
출처 표기는 사용 권한 확인과 별도 항목으로 관리합니다. 출처 목록 자체를 이용 허가로 처리하지 않습니다.

## 완성 기사의 구조

| 항목 | 내용 규칙 |
| --- | --- |
| 분류 | 정책·입시·학교생활 등 사이트의 분류 체계에 맞춤 |
| 제목 | 핵심 변화가 드러나며 근거보다 과장하지 않음 |
| 제목 아래 요약 | 2문장: 무슨 변화인가 / 왜 중요한가. 기기 폭에 따라 실제 줄 수는 달라짐 |
| 세부 항목 | 변화 내용, 적용 대상, 시점, 조건, 예외 등을 소제목으로 구분 |
| 핵심 정보 카드 | 기사에 맞는 4~8개 정보. 모든 기사에 같은 항목을 강제하지 않음 |
| 독자별 안내 | 학생·학부모·교사를 위한 확인·준비·생각할 점 |
| 출처 | 원문 기사와 실제 확인한 근거 목록 |
| 편집 기록 | 기사 버전, 재검증 결과, 최종 승인 시간 |

독자별 안내는 확인된 사실과 편집자의 제안을 구분합니다.
제안을 공식 정책이나 의무로 바꾸어 쓰지 않습니다.
정보가 없는 항목은 임의로 채우지 않고 생략하거나 확인이 필요하다고 표시합니다.

## 독자별 안내 디자인

완성 기사의 독자별 안내는 하나의 패널 안에 기사 제목과 학생·학부모·교사 세 영역을 배치합니다.
각 영역에는 아이콘, '먼저 확인하세요', '이렇게 준비해보세요' 등의 짧은 안내를 넣습니다.
항목 이름은 기사 성격에 맞게 바꿀 수 있습니다.
PC에서는 세 열, 모바일에서는 세로로 표시하며 기사 내용이 달라지면 안내도 다시 생성·편집합니다.
실제 HTML/CSS와 기사 미리보기는 4단계에서 구현합니다.

## 데이터 구조

현재 실제 저장되는 구조:

| 데이터 | 필드 |
| --- | --- |
| 원문 | id, original_text, original_url, revision, source_revision, created_at, updated_at |
| 근거 | id, article_id, name, kind, url, locator, excerpt, created_at |
| API 상태 | verification_status=not_run, checks=[], draft=null, can_publish=false |

근거 종류는 official / press / other이며 사용자가 선택하는 분류입니다.
원문 수정 시 revision, 근거 추가 시 source_revision이 올라갑니다.
변경되지 않은 원문을 다시 저장하면 revision을 올리지 않습니다.
다른 화면에서 버전이 변경되면 이전 버전으로 저장하는 요청을 거절합니다.

이후 단계에서 추가할 구조:

| 데이터 | 주요 필드 |
| --- | --- |
| 사실 주장 | claim_id, phase(original/draft), 기사 내 위치, 원래 문장, 비교할 사실, 대상·시점·조건 |
| 판정 | claim_id, verdict, 근거 ID, 발췌·위치, reason, 수정할 사실, checked_at |
| 근거 확인 | 발표일·적용 기간, 실제 읽은 내용, 조회 시간, 수집 성공 여부 |
| 재작성본 | draft_revision, category, title, summary[2], sections, key_facts, audience_guidance, sources |
| 검증 보고서 | original_revision, source_revision, draft_revision, 보고서 ID, 진행 상태 |
| 승인 | 현재 버전의 검증 보고서 ID, approved_by, approved_at |
| 변경 이력 | 이전 원문·근거·기사 내용과 변경 시간 |
| 발행 결과 | 최종 승인 ID, 최종 기사 내용, 게시 위치, 게시 시간 |

## 발행 조건

재작성본의 사실 주장에 불일치·조건 보완 필요·확인 불가가 남으면 발행 준비 완료로 처리하지 않습니다.
근거를 확보하거나 표현을 수정·제외하고 재검증한 다음 사람이 최종 확인합니다.
근거가 필요한 사실 주장과 편집자의 제안을 구분하여 판정합니다.

원문·근거·재작성본이 바뀌면 해당 버전에 연결된 이전 검증과 승인은 유효하지 않습니다.
기사 내용과 근거의 버전이 모두 최신 검증 보고서 및 승인 기록과 맞을 때 발행합니다.
브라우저에서 임의로 '승인됨' 표시를 바꾸어도 서버의 발행 조건을 통과할 수 없게 구현합니다.

최종 버전에는 사람의 승인과 승인된 HTML·JSON 다운로드를 연결했습니다. approval_status와 can_export로 상태를 확인합니다.
실제 웹사이트 발행은 별도여서 can_publish는 false입니다.

## 단계별 확인 기준

1단계: 저장·조회, 서버 재시작 후 보존, 빈 입력 거절, 잘못된 URL 거절, 오래된 버전의 저장 거절.
2단계: 날짜 오류, 대상·적용 연도 오류, 빠진 예외, 근거 부족, 서로 다른 근거의 충돌을 구분.
3단계: 원문 오류를 근거로 수정하여 재작성하고, 새 사실이나 과장을 임의로 넣지 않는지 확인.
4단계: PC·모바일 레이아웃, 수정 반영, 독자별 안내의 내용과 디자인 확인.
5단계: 재작성 중 생긴 오류를 검출하고 수정 이후 이전 승인으로 발행할 수 없는지 확인.
6단계: 기존 사이트의 실제 데이터 구조에 맞춘 내보내기와 게시 전 미리보기 확인.

## 다음 구현의 시작점

원문 검증·재작성·초안 전체 검증·사람의 승인·기사 내보내기까지 구현했습니다.
다음은 기존 웹사이트의 실제 기사 형식과 게시 방법을 확인하는 연결 작업입니다.
API 키는 계속 서버에서 관리합니다. 실제 기사와 근거로 판정 품질을 확인하며 사용하세요.
